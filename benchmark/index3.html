تحيز Checkov & محدودية عينات C#

دليل شامل يوضح بالظبط إزاي حلّينا المشكلتين الكبار في مجلد الـ benchmark بكل شفافية ومنهجية علمية دقيقة — بدون تخبيّة أي نقاط ضعف وبدون أرقام مضللة.

⚡

المشكلة الأولى: تحيز Checkov

مشاريع TerraGoat و CfnGoat الإجابات فيها جاية من Checkov، وعلشان SentinelAI بيستخدم Checkov فالمقارنة بتبقى مش عادلة للمنافسين.

🔷

المشكلة الثانية: كود C# القليل

عدم وجود standard benchmark لـ C# زي Java OWASP خلى عينات الـ C# محصورة في الـ flagship fixture وشوية near-misses يدوية.

⚖️ التحدي الأول والتفصيلي

1️⃣ مشكلة تحيز Checkov في مشاريع الـ Infra

في مشاريع TerraGoat و CfnGoat، الـ ground truth اتكتبت بناءً على نتائج أداة Checkov نفسها. ولأن SentinelAI جوا مكوناته الداخلية بيشغل Checkov في الـ infra layer، ده بيدينا ميزة غير عادلة لو قارنّا نفسنا بـ SonarQube أو Snyk على المشاريع دي.

💡

الحل الهندسي: الفصل الصارم والتدرج (Corpus Tiering)

قسمنا الـ Benchmark Corpus لمستويين منفصلين تماماً في الكود والتقارير: مستوى Headline Scanner-Neutral للمقارنة العادلة مع المنافسين، ومستوى Internal Tool-Validation للاختبار الداخلي.
الخطوة 01
عزل الـ Headline Set
مقارنة الـ Precision/Recall الرسمية مع SonarQube و Snyk بتعتمد فقط على Kubernetes-Goat و Clean-Samples لأنهم Scanner-Neutral.
الخطوة 02
حصر Checkov للـ Validation
مشاريع TerraGoat و CfnGoat بتتسمى "Internal Validation Sets" — بتستخدم لتأكيد شغل SentinelAI الداخلي فقط ومش كادعاء رسمي ضدهم.
الخطوة 03
وسم البيانات بـ Provenance
كل ملف JSON في الـ ground truth وكل item معلّم بـ field صريح يوضح هل هو scanner-neutral أو tool-derived:checkov.
benchmark/ground_truth/terragoat.json — التوسيم الصريح للتحيز JSON Header
{
  "project": "terragoat",
  "provenance": "Ground truth derived from TerraGoat's Checkov output... Cross-tool recall is biased toward Checkov; use for within-SentinelAI validation, NOT as headline cross-tool fairness claim.",
  "ground_truth_bias": "tool-derived:checkov",
  "items": [...]
}
🔷 التحدي الثاني والتفصيلي

2️⃣ مشكلة محدودية عينات C# Ground Truth

على عكس لغة Java اللي فيها OWASP Benchmark جاهز وفيه أكتر من 2000+ عينة اختبار، مفيش standard security benchmark عالمي لـ C#. لذلك عينات C# في المشروع صغيرة ومحصورة في الـ flagship fixture وشوية near-misses يدوية.

🛡️

الحل الهندسي: منهجية الألياف المزدوجة والتأطير الصادق

عالجنا قلة الكود باستراتيجية مزدوجة: تأطير النتايج بصدق علمي كـ "Indicative" وعدم ادعاء دقة إحصائية ضخمة، مع إنشاء عينات Near-Miss مقترنة لقياس الـ False Positives بدقة.
الاستراتيجية 01
التأطير الصريح (Honest Framing)
التصريح في كل التقارير والـ README بإن نتائج C# هي "Qualitative Indicative Proof" بتثبت إن السلسلة شغال، وليست "Statistical Benchmark".
الاستراتيجية 02
مزدوجات Near-Miss الأقواس
لكل ثغرة في C# (زي CWE-89 SQLi أو CWE-502 Unsafe Deserialization)، عملنا كود مقابل سليم تماماً في clean-samples لاختبار الـ False Positives.
الاستراتيجية 03
التركيز على Attack-Chain Hop
استخدام عينات C# في إثبات خطوة الربط بين الطبقات (Dep → Code → Infra)، حيث الجودة وإعادة بناء السلسلة أهم من العدد الإحصائي.
benchmark/clean-samples/authored/SafeDeserialization.cs — العينة المقترنة النظيفة C# Near-Miss Control
// SafeDeserialization.cs — Near-miss clean sample for CWE-502
public class SafeDeserializer {
  public static OrderDto Parse(string jsonInput) {
    // Safe: System.Text.Json into fixed DTO type (No TypeNameHandling.All / no polymorphic types)
    return JsonSerializer.Deserialize<OrderDto>(jsonInput);
  }
}
