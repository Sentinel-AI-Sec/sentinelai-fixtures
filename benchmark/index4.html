معالجة تحيز Checkov & محدودية C# Benchmark

كيف تحول نقاط الضعف المنهجية إلى أدلة على نضج التفكير العلمي وحصانة العرض أمام المناقشين (Examiner-Proof Methodology).

💬 مبدأ مناقشة مشاريع التخرج: "في مشاريع التخرج، النقطة السلبية الموثقة والمصرح بها صراحةً (Disclosed Limitation) لا تُخصم عليها درجات — بل تُحسب كدليل على النضج العلمي. بينما النقطة الخفية التي يكتشفها المناقش بنفسه هي التي تدمر المصداقية."
⚖️

المشكلة الأولى: تحيز Checkov (Checkov Bias)

393 عينة من أصل 430 في cfngoat و terragoat مصدرها أداة Checkov نفسها. ولأن SentinelAI يستخدم Checkov، فالمقارنة المباشرة تكون كمَن يحل امتحاناً يملك إجابته النموذجية.

🔷

المشكلة الثانية: عدم وجود Benchmark لـ C#

بخلاف لغة Java (التي تمتلك OWASP Benchmark بـ 2000+ نموذج)، لا يوجد benchmark قياسي لـ C#. بيانات C# محصورة في 21 عينة يدويًا من الـ flagship fixture الخاص بالمشروع.

🎯 المشكلة الأولى والتفصيلية

1️⃣ تحيز Checkov Bias — الحلول والاستراتيجيات

الحقيقة العلمية: لا يمكن إعادة كتابة وتوثيق 393 عينة يدوياً في الوقت المتبقي. والهدف هو تحييد الأثر على الادعاء الرئيسي (Headline Claim) وليس إلغاء البيانات من المشروع.

الحل 1a: عدم دمج الأرقام مطلقاً والتقرير حسب فئة المصدر (Provenance Segregation)
Must Do (إجباري)

أهم خطوة على الإطلاق ولن تكلفك أي كود — مجرد انضباط في طريقة التقرير في SEC-39:

  • الادعاء الرئيسي (Headline Metrics): يُحسب فقط من المجموعات المحايدة scanner-neutral + hand-labeled (مثل kubernetes-goat, csharp, clean-samples, و neutral-iac).
  • مجموعات Checkov: تُوضع في جدول منفصل تماماً مرمز بوضوح: "Checkov-anchored — validates SentinelAI's detection consistency, not a fair cross-tool comparison."
الحل 1b: إعادة صياغة هدف عينات Checkov (Coverage & Scale Validation)
Should Do (موصى به)

لا تقدم cfngoat/terragoat على أنها "SentinelAI يغلب SonarQube"، بل قدمها كـ اختبار قدرة وسعة (Scale & Coverage Validation):

"عبر 393 إعداداً خاطئاً في الـ Infrastructure تغطي 5 مقدمي خدمات سحابية، أثبت خط أنبوب SentinelAI قدرته على توحيد وتجميع المشاكل وبناء السلاسل دون فقدان أي بيانات."

الحل 1c: إنشاء مجموعة IaC محايدة تماماً (neutral-iac.json)
Nice to Have / Actionable

إنشاء ملف جديد benchmark/ground_truth/neutral-iac.json يتكون من 12–15 ثغرة محايدة ومستقلة عن أي أداة، ومكتوبة على مستوى Vulnerability Class وليس Scanner Rule.

🔷 المشكلة الثانية والتفصيلية

2️⃣ محدودية عينات C# Benchmark — الحلول والاستراتيجيات

الحقيقة العلمية: لا يوجد OWASP Benchmark لـ C# عالمياً، ولا يُتوقع منك بناء واحد في مشروع تخرج. المعيار هو كيف تتعامل مع هذه المحدودية كعالم ومطوّر محترف.

الحل 2a: التصريح بالمحدودية في مقدمة التقرير (Headline Caveat)
Must Do (إجباري)

اجعل تنويه المحدودية عنواناً رئيسياً وليس هامشاً سفلياً. إعلان المحدودية قبل أن يكتشفها المناقش يحول نقطة الضعف إلى دليل على النضج العلمي.

الحل 2b: ربط حزم C# بـ CVEs حقيقية من مكتبة OSV
Should Do (موصى به)

بدلاً من أن تكون التسميات ذاتية فقط ("Mohamed says so")، ربط الـ 7 مكتبات في NuGet بأرقام CVE رسمية عبر تشغيل OSV-Scanner على مشروع C# بـ SentinelAI.

الحل 2d: إعادة تأطير ادعاء C# كـ Capability Demonstration
Should Do (موصى به)

لا تدعي "SentinelAI لديه دقة X% في C#"؛ بل ادعي: "على عينة C#، يثبت SentinelAI القدرة الفريدة على بناء السلسلة بين الطبقات (CWE-502 ← Wildcard IAM ← S3) والتي تعجز أي أداة أحادية الطبقة عن اكتشافها."

📌 النص الموصى به للتصريح (للإضافة في benchmark/README.md والتقرير):

"C# ground-truth scope and limitation: Unlike Java, which has the OWASP Benchmark (thousands of labeled cases), no standard C#/.NET security benchmark exists. The C# ground truth here is therefore limited to 21 hand-labeled findings from a single, self-authored flagship fixture. These results are indicative, not statistically rigorous. Accordingly, the C# set is used to demonstrate SentinelAI's cross-layer chaining capability (CWE-502 → wildcard-IAM → S3), not to make statistical precision/recall claims. Cross-tool statistical comparison relies on the scanner-neutral sets."

البرومبت المكتوب لتوليد neutral-iac.json

يمكن استخدام هذا البرومبت لتوليد الملف المحايد الخاص بالـ Infrastructure عبر AI أو Claude Code:

Prompt for creating benchmark/ground_truth/neutral-iac.json SEC-38 Specification
Still sentinelai-fixtures, SEC-38 — create a NEW ground-truth set: benchmark/ground_truth/neutral-iac.json.
Touch no existing ground-truth file. This set must be tool-neutral — its whole purpose is a fair cross-tool comparison,
so labels must NOT be tied to any one scanner's rules.

Goal: ~12–15 IaC misconfigurations, labeled at the vulnerability level (not the scanner-rule level),
each drawn from resources already in the vendored terragoat/cfngoat trees but described independently of Checkov.

Selection rules (strict):
1. Choose only high-consensus misconfigurations (public storage, unencrypted sensitive storage, open 0.0.0.0/0 on sensitive ports, wildcard IAM, hardcoded secret).
2. One item per real vulnerability, not per rule (collapse S3 7-rows into 1-2 distinct vulnerabilities).
3. Spread across providers (aws / azure / gcp).
4. Use CWE IDs only (e.g. CWE-284) — NO CKV or scanner rule IDs.

Schema:
{
  "id": "GT-001",
  "layer": "infra",
  "file": "path in vendored tree",
  "resource_or_line": "resource address",
  "expected_label": "real_finding",
  "expected_category": "public-storage | open-ingress | wildcard-iam | unencrypted-storage",
  "cwe_or_rule": "CWE-284",
  "notes": "Vulnerability description in tool-neutral language",
  "source_class": "neutral-handlabeled"
}
🧠 التقييم الهندي الفني

رأي الخبير وتقييم الـ Prompt (Expert Point of View)

تحليل نقدي لمعمارية ورؤية هذا الـ البرومبت ولماذا يعتبر الحل الأمثل لمشروع تخرج بمستوى إنتاجي:

💡 النظرة الفنية والتحليلية للـ Prompt:

1. معالجة الجذر بدلاً من العَرَض (Root-Cause Fix)

البرومبت لا يحاول "تجميل" أسماء قواعد Checkov، بل يقوم بإنشاء شريحة ذهبية محايدة (Gold Standard Dataset) من 12-15 عنصراً تُبنى مباشرة على مفاهيم الـ Vulnerability Class والـ CWE (مثل CWE-284)، مما يجعل الادعاء مستحيلاً أن يُطعن فيه من قِبل أي مناقش.

2. تجميع القواعد المتعاددة (Rule Collapsing)

أهم عبقرية في البرومبت هي تجميع القواعد (Collapsing). الـ Scanners التلقائية تخرج 7 تحذيرات مختلفة لـ S3 Bucket واحد bad. البرومبت يدمجها في ثغرة حقيقية واحدة يراها الإنسان، وهو ما يطابق طريقة التقييم البشري الحقيقي.

3. التوزيع على الـ Cloud Providers

اشتراط توزيع الثغرات بين AWS و Azure و GCP يضمن عدم تحيز الاختبار لمزود سحابي معين، مما يعطي انطباعاً بقوة التغطية والشمولية للنظام أثناء العرض النهائي.

4. الانضباط في مراجعة الكود (Reviewer Protocol)

طلب عدم تنفيذ git commit فوراً والاطلاع على git diff --stat يعكس احترافية عالية تمنع دخول أي بيانات غير مفحوصة أو تحمل بالخطأ معرفات Checkov كودية إلى الـ Benchmark الرسمي.
