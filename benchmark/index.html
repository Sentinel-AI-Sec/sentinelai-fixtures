🔒 القاعدة الأهم

قاعدة "Never Embedded"

الـ benchmark لا يُضاف أبدًا لقاعدة المعرفة (Qdrant / RAG). ده مش مجرد وعد على الورق — محمي بكود فعلي.

🚨

ممنوع تمامًا: إضافة أي ملف من benchmark/ للـ RAG

لو حصل ده، هيتخرب حاجتين مرة واحدة:
① قاعدة المعرفة هتتلوّث ببيانات اختبار — وده بيخلي النظام يحفظ الإجابات بدل ما يتعلم فعلًا.
② القياس هيبقى فاسد — النظام هيكون "ماشي على الإجابة النموذجية" فأي درجة هيجيبها مش حقيقية.


الحل: ملف اسمه .no-ingest موجود في جذر المجلد. الـ ingestion pipeline لازم يوقف ويصرخ لما يلاقيه — مش يتجاوزه بصمت.

⚠️ ليه "بيصرخ" ومش بس "بيتجاوز"؟

لو الـ pipeline اتجاوز الملف بصمت، ممكن يفضل ميتم اكتشاف المشكلة لأيام. لما بيوقف بـ error واضح، المشكلة بتتكشف فورًا في أول مرة حد يحاول يضيف الـ benchmark غلطًا.

📋 هيكل البيانات

إزاي بيتكتب الـ Ground Truth؟

كل item في الـ benchmark بيتوصف بهيكل JSON موحد يحدد الإجابة الصح لكل حالة.

ground_truth / csharp.json — مثال على item واحد (GT-001)
"id"
معرّف فريد ومستقر زي GT-001. بيفضل ثابت لو اتعملت تعديلات تانية.
"layer"
الطبقة اللي فيها المشكلة: code (كود تطبيق) أو dep (dependency) أو infra (infrastructure).
"file"
المسار للملف relative لمشروع الاختبار اللي فيه المشكلة.
"resource_or_line"
المكان المحدد: اسم الـ resource أو رقم السطر داخل الملف.
"expected_label"
الإجابة الصح: real_finding (ثغرة حقيقية) أو not_a_finding (مفيش مشكلة). ده الـ ground truth اللي بنقيس عليه.
"expected_category"
نوع المشكلة بصورة مقروءة زي sql-injection أو hardcoded-api-key.
"cwe_or_rule"
المرجع القياسي: رقم الـ CWE زي CWE-89 أو rule id من الـ scanner.
"notes"
الشرح: ليه ده ثغرة حقيقية أو مش ثغرة. الـ reasoning مهم للمراجعة.
📊 المقاييس المهمة

Precision & Recall — ليه الاتنين مع بعض؟

الـ benchmark بيمكّن حساب Precision و Recall لـ SentinelAI مقارنةً بـ SonarQube و Snyk. لازم تتحسب الاتنين — الرقم اللحلو بس مش كافي.

🎯 Precision

من كل اللي النظام قال عليه "مشكلة" — كام واحدة كانت فعلًا مشكلة؟ Precision عالية = false positives قليلة = المطور مش هيتجاهل التحذيرات.

Precision = True Positives ÷ (TP + False Positives)

📡 Recall

من كل المشاكل الحقيقية اللي موجودة — النظام اكتشف كام منها؟ Recall منخفض = النظام بيخبي المشاكل — خطير حتى لو Precision عالية.

Recall = True Positives ÷ (TP + False Negatives)
⚠️ القاعدة: لازم الاتنين مع بعض

Precision عالية جدًا وRecall منخفض معناه إن النظام بيخبي كل المشاكل ومش بيعلّم على أي حاجة. ده مش نجاح — ده فشل بطريقة تانية. الـ benchmark بيضمن إن الاتنين يتحسبوا وما يتخبوش.

🔍 شفافية مهمة

حدود وتحيزات موثقة بصدق

جزء مهم من الـ benchmark هو توثيق حدوده — مش إخفاؤها.

تحيز #1

Checkov-biased Ground Truth (CfnGoat & TerraGoat)

الـ ground truth لهذين المشروعين مبنية على نتايج Checkov. وبما إن SentinelAI بيستخدم Checkov، المقارنة مع SonarQube أو Snyk على هذين المشروعين مش عادلة — لأن SentinelAI بيبدأ بميزة. ده متوثق في كل ground truth file.

الحل: المقارنة الرئيسية مع المنافسين بتعتمد على الـ scanner-neutral sets (hand-labeled & clean-samples) مش Checkov sets.

حد #2

C# Benchmark صغير وغير قياسي

مفيش benchmark C# معياري موجود (زي OWASP Benchmark للجافا). ده معناه إن الـ C# ground truth صغير ومعمول يدوي. النتايج على C# استرشادية، مش إحصائية — والمشروع بيقول ده صريح ومش بيخبيه.
